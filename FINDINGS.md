## 1. Cost audit — transcript-to-node pipeline (2026-07-24, rounds 1-6)

Snapshot taken 2026-07-24, before any cost optimization work. Real usage testing showed roughly **$0.0667 per minute of session time**, and ending a solo session alone cost ~$0.07 (the "Linking ideas…" wrap-up step). This section is a factual record of exactly what the pipeline sent to which model, how often, round by round, so the reasoning isn't lost as the pipeline got cheaper. Current settings resulting from this work are summarized in [PLAN.md §10](PLAN.md#10-llm-cost--pipeline-economics).

### The three LLM call sites (as of the 2026-07-24 snapshot)

All three call the Anthropic API directly via the official SDK (`base44/shared/claude.ts`), not Base44's built-in `InvokeLLM` — that switch was made deliberately, to get prompt caching (`cache_control`) and forced tool-use, neither of which `InvokeLLM` exposed. Keep this in mind before reverting any of these to `InvokeLLM` — it would mean giving those two things up.

**1. Stage-2 rough guess — `classify-partial` function.**
- Model: `claude-haiku-4-5-20251001`.
- Trigger: mic-live sessions only, debounced 500ms while partial (non-final) transcript text is still stabilizing mid-utterance (`Board.jsx` `handleMicPartial`). Fires at most once per ~500ms pause in an in-progress utterance, and stops firing early once confidence ≥ 0.9 settles it.
- Payload: static cached system prompt (~250 tokens) + one line, the current partial utterance text. Tiny, cheap, not a meaningful cost driver.

**2. Tier 1 classification — `process-session` function.**
- Model: `claude-haiku-4-5-20251001`.
- Trigger:
  - **Live sessions (mic or bot):** once per finalized utterance, fired immediately and in parallel the instant each utterance ends (`liveProcess()` in `Board.jsx`) — never batched, never waits for a previous call to finish.
  - **Import / wrap-up (non-live):** looped, pulling up to `IMPORT_BATCH_SIZE = 12` unprocessed utterances per call until none remain.
- Payload per call:
  - System prompt: large (~2,200 words, the full classification taxonomy + worked examples) but marked `cache_control: ephemeral` and byte-identical every call, so after the first call of a session it's served from Anthropic's prompt cache, not re-billed at full input price.
  - User message (NOT cached — this part is different on every call):
    - **The full list of every visible node in the session so far** (id/type/title/summary, summary truncated to 160 chars) — `openList`, uncapped, refetched and resent on every single utterance. This is the one part of the "whole conversation" that genuinely does get resent each time — not the raw transcript, but the growing node graph. It grows linearly with session length, so token cost per utterance grows the longer a session runs.
    - A 3-utterance sliding-window of recent context (so a thought split across a pause reads as one thought).
    - The new utterance(s) to classify (1 in live mode, up to 12 in import mode).
  - Forced tool-use (`tool_choice: {type: "tool", ...}`) for structured output — output tokens are small and cheap regardless.
- Result: emits `SessionOp` rows (`create_node` / `attach_node` / `create_edge`) per decision. The frontend never re-fetches or regenerates the board in response — it applies each op to in-memory state as it streams in via realtime. This delta-based rendering already existed and was not a cost problem — the cost lever here was the growing `openList` payload, not board re-rendering.

**3. Tier 2 consolidation ("linking") — `consolidate-session` function.**
- Model (originally): `claude-sonnet-5`, called with `thinking: { type: "adaptive" }` (the model decides how much to reason; thinking tokens are billed as output tokens, at Sonnet's output rate — this is materially more expensive per call than Tier 1's plain Haiku call, both in $/token and typically in token count).
- Trigger — **this ran far more often than "once at the end":**
  - **Periodically during a live session:** every 5 utterances successfully processed by Tier 1 (`sinceConsolidateRef.current >= 5` in `Board.jsx`), fire-and-forget, not awaited by the UI. A single 10-minute talking session with ~40-60 utterances triggered this **6-12 times before it even ended.**
  - **Once more at session end** ("linking" phase, `needsLinking` in `Board.jsx`'s wrap-up effect) — this is the specific call users see as "Linking ideas…".
- Payload per call: **the entire node graph for the session, resent from scratch every time** — every node (up to 200, id/type/title/summary truncated to 200 chars) plus every existing edge among them (up to 500) — not windowed, not delta'd, not cached.
- The system prompt here was passed as a plain string (`system: opts.system` in `reasonForJson`, `base44/shared/claude.ts`), not wrapped with `cache_control` the way Tier 1's is — so Tier 2's ~500-word system prompt was billed in full on every single call too, zero caching benefit on this call site.
- Result: `merge_nodes` / `create_edge` ops, same ops-log delivery as Tier 1.

### What wasn't tracked (as of the snapshot)
Anthropic's `usage` object (input/output/cache tokens) was returned by both `classifyWithTool` and `reasonForJson` but discarded by every caller — never logged, never persisted anywhere. There was no way to see actual token/cost breakdown per call site from this app's own data; the $0.0667/min figure came from the Anthropic Console, not from anything Tackly logged.

### Findings — where the cost actually went
1. **Tier 2 firing every 5 utterances live, not just once at the end, was almost certainly the dominant cost.** It was Sonnet (pricier per token than Haiku) with adaptive thinking (thinking tokens bill as output, typically the priciest tokens), on an uncached system prompt, resending the full node+edge graph — repeatedly throughout a single live session, not once.
2. **Tier 2's system prompt wasn't cached at all** (missing `cache_control`, unlike Tier 1) — a straightforward fix with no behavior change.
3. **Tier 1's `openList` (all visible nodes, every utterance) was uncapped and uncached**, so cost-per-utterance crept up over the course of a long session even though each individual call was cheap.
4. **No token/cost visibility** — the app couldn't answer "how much did this session cost" from its own data, only from the Anthropic Console in aggregate.
5. **The end-of-session Tier 2 pass duplicated most of what the periodic live passes already did** — since Tier 2 already ran repeatedly throughout the live session, the final "Linking ideas…" pass was mostly re-processing an already-mostly-merged graph, for a comparatively small amount of new material. Left as-is (still runs once at session end) — only the live frequency and model changed, see Round 1 below.

### Round 1 — changes applied (2026-07-24, based on user decisions)
Two decisions were confirmed and applied:
- **Live Tier-2 frequency: every 5 utterances → every 20** (`sinceConsolidateRef` check in `Board.jsx`'s `liveProcess`). Cuts live consolidation calls roughly 4x for a typical session; the end-of-session pass is unchanged and still catches anything the wider live interval missed.
- **Tier 2 model: Sonnet + adaptive thinking → Haiku 4.5, via a forced tool call** (`consolidate-session/entry.ts` — `TIER2_MODEL`, new `TIER2_TOOL`/`record_consolidation` schema, switched from `reasonForJson` to `classifyWithTool`). This was explicitly called out as "try it and see" rather than a confident final answer — merge/cross-link judgment is a harder call than Tier-1's per-utterance classification, so watch real sessions for missed merges or bad edges. **Agreed fallback if Haiku's judgment proves too weak: Sonnet with thinking OFF (not adaptive)** — still drops the thinking-token bill (the biggest single line item) while keeping Sonnet's stronger reasoning; swap `TIER2_MODEL` back and pass `thinking` as omitted/off rather than `{type: "adaptive"}`. Do not silently revert to the original Sonnet+adaptive-thinking setup without a fresh decision — that was the confirmed-expensive configuration this change was meant to replace.
- Switching to a forced tool call (`classifyWithTool`) also fixed finding #2 above for free — its system prompt is `cache_control`-cached the same way Tier 1's is, unlike the old `reasonForJson` path.
- **Not changed**: openList capping (#3) and usage/cost logging (#4) remained open — addressed in Round 2 below.

### Round 2 (same day, after real-world testing showed ~$0.20 for a 6-min session)

Round 1 cut the dominant cost driver but a real 6-minute session still ran ~$0.033/min, and the user flagged that most real sessions run 15-45 minutes — long enough for Tier 1's uncapped `openList` (finding #3) to actually matter, not just compound in theory. Node-classification quality was confirmed good and untouched by any of this — everything below is cost/plumbing only, no taxonomy or prompt-behavior changes.

**Pricing used for all estimates below** (checked live against `platform.claude.com/docs/en/docs/about-claude/pricing` on 2026-07-24 — Sonnet 5 shows introductory pricing through 2026-08-31, standard pricing is higher after):
| Model | Input | 5m cache write | Cache read | Output |
|---|---|---|---|---|
| Haiku 4.5 | $1/MTok | $1.25/MTok | $0.10/MTok | $5/MTok |
| Sonnet 5 (through 2026-08-31) | $2/MTok | $2.50/MTok | $0.20/MTok | $10/MTok |

**Changes made:**
1. **`openList` windowing (finding #3), applied.** `process-session/entry.ts`: instead of sending every visible node every call, the model is now shown every `topic`-type node (the natural parent for a whole branch) + every still-`open` question/risk/action (the likeliest attach target for what's said next) + the most recent `OPEN_LIST_RECENCY = 50` nodes for everything else. Bounds cost growth on a long session instead of it creeping up the whole way through. **Deliberate tradeoff, not a free lunch:** a very old, already-resolved, non-topic node can age out of the window and stop being offered as a possible parent/attach target once a session gets long enough. Watch for "why didn't this attach to the thing I said 40 minutes ago" reports specifically on long sessions — if that becomes a real problem, raise `OPEN_LIST_RECENCY` rather than reverting the windowing outright.
2. **Filler pre-filter, applied (`process-session/entry.ts`, `FILLER_WORDS`/`isPureFiller`).** An utterance that's 1-2 words and entirely acknowledgement/filler ("okay", "yeah", "right", "got it", "hi") is dropped before it ever reaches the model — it was going to come back "skip" anyway (see `TIER1_SYSTEM`'s own SKIP bucket), so this just saves paying Haiku to confirm what a word list already knows. Deliberately excludes bare "yes"/"no" (a one-word answer to a real question is substantive content, not filler) and requires the WHOLE utterance to match, so "yeah, ship Friday" still reaches the model. In live mode (1 utterance per call) a pure-filler utterance now skips the API call entirely; in import/wrap-up batches, filler utterances are filtered out of the batch sent to the model (via a `classifyIdx` remap back to real batch positions) rather than being dropped from the whole batch.
3. **Cost tracking, built (all three call sites + `Session.llm_cost_usd` + `base44/shared/claude.ts` `estimateCostUsd`).** Every Anthropic call's real token usage (input/cache-write/cache-read/output, straight from Anthropic's own `usage` object) is converted to an estimated $ cost via the table above and `$inc`-ed onto `Session.llm_cost_usd`. This is an *estimate* for relative tracking (before/after a pipeline change, admin $/min) — no volume discounts or batch pricing accounted for, so don't expect it to match the Anthropic invoice to the cent. Historical sessions from before this deploy had no cost recorded (the field didn't exist yet) — the admin average reads artificially low until enough new sessions accumulate real data.
4. **Admin visibility, built.** `admin-session-stats` returns `avg_cost_per_minute_usd` (sum of `llm_cost_usd` ÷ sum of `billed_ms` in minutes, completed sessions only — an in-progress session's cost-so-far would understate its eventual rate) alongside `total_llm_cost_usd` and `billed_minutes`. Surfaced as a stat tile on `/admin` (`Overview.jsx`).

**A real bug found and fixed while verifying this (worth remembering for any future Deno function work here):** the cost `$inc` was originally written fire-and-forget (`.catch(() => {})`, not awaited) right before each function's return. Verified via a live test against production (`npx base44 exec` + `functions.invoke`) that this silently lost the update in `consolidate-session` specifically — when the model proposes zero merges and zero edges, there's essentially no other awaited work left between the cost update and the function's return, so the isolate returns before the fire-and-forget write lands. It worked fine in `process-session`, which has plenty of awaited work (node/edge/op creation) after the same pattern — same bug, just usually masked by other work absorbing the race. **Lesson: don't fire-and-forget a write you actually need, this close to a function's return, without confirming the runtime guarantees background completion (Base44's doesn't appear to) — await it.** All three call sites now await the cost update explicitly.

**Verification method:** tested directly against the live production app via `npx base44 exec` (creating real scratch `Session`/`Utterance`/`Node` rows, invoking the deployed `process-session`/`consolidate-session`/`admin-session-stats` functions exactly as the frontend does, reading back `Session.llm_cost_usd` to confirm accumulation), then deleting the scratch data — not simulated locally, since Deno secrets (`ANTHROPIC_API_KEY`) aren't reachable from local tooling.

**Not changed, still open at this point:** Tier-2's node/edge payload remained unwindowed (full graph, up to 200 nodes/500 edges) — left as-is deliberately, since duplicate/cross-link detection benefits from seeing the whole graph regardless of recency, and Tier-2 was both cheaper (Haiku) and far less frequent (every 20 utterances + once at end) now than before Round 1, so the remaining savings from windowing it too would be smaller than what windowing Tier-1 bought.

### Round 3 (same day, real 6-min session still ~$0.33 after rounds 1-2 — ~50 nodes, most of that likely fixed by the anti-fragmentation prompt tuning in PLAN.md §11 rather than further cost cuts)

**Live Tier-1 batching, applied.** Every call still paid a fixed tool-use/system-prompt overhead (~500-600 tokens for Haiku with a forced tool choice, per Anthropic's own tool-use pricing docs) regardless of how little it classified — and until now, live capture fired one `process-session` call per finalized utterance. Client now queues finalized utterances (`Board.jsx`, `pendingQueueRef`/`queueForProcessing`/`flushQueue`) and flushes as ONE batched call after `BATCH_DEBOUNCE_MS = 2500` of no new utterance, or the instant the queue hits `BATCH_MAX_SIZE = 4` — whichever comes first, bounding added latency to a few seconds either way. Applies to both mic-live and bot-live paths (previously bot ingestion already received utterances in small arrays from the webhook/poll but still fired one call per utterance inside a `forEach` — now batched too). `endLiveSession` flushes the queue and awaits it before flipping session status, so nothing gets stranded read for the wrap-up pass.

`process-session` already supported a multi-utterance batch (import mode always did, `IMPORT_BATCH_SIZE = 12`) so the backend risk here was low — the one real addition was **multi-provisional support**: previously only utterance-position-0 in a batch could claim a `provisional_node_id` (fine when live batches were always size 1); now a batch can carry several already-forming provisional nodes at once, so the API takes a `provisionals` map (`{utterance_id: node_id}`) instead of a single id, and both the finalize-in-place logic and the false-start hide-cleanup loop over every entry in that map, not just one. `provisional_node_id` (singular) is still accepted for backward compatibility with any in-flight client mid-deploy.

**Verified end-to-end against production** (`npx base44 exec`, scratch session + 2 provisional nodes + a batched `process-session` call carrying both): both provisional nodes finalized in place correctly (no duplicate stray nodes), and the same call classified a "starting balance" statement as `fact` and a cost-reduction goal as `plan` — confirming both the batching/multi-provisional plumbing and the new taxonomy types work together correctly.

**Canvas spacing, applied.** Layout constants in `process-session/entry.ts` (`placeNode`) bumped up — `STEP_Y` 200→260, `STEP_X` 280→340, `CLR_X` 250→300, `CLR_Y` 165→200 — new nodes get noticeably more breathing room from their neighbors per the "feels too tightly packed" feedback, without changing the underlying tree-layout algorithm.

**"Tackling…" ghost node, applied.** `GhostNodeCard.jsx` now layers a diagonal light-sweep shimmer (new `shimmer` keyframe/animation in `tailwind.config.js`) on top of the existing breathing-pulse, so the placeholder reads as "actively being built" rather than a static pulsing box.

**Floating live transcript, applied.** New `src/components/FloatingTranscript.jsx` — a desktop-only (`hidden lg:block`), low-opacity (40%) ambient preview of the last 6 utterances that floats over the canvas (top-right, rendered as an untransformed sibling in `Board.jsx`'s viewport div, same pattern as the zoom controls — so it's unaffected by pan/zoom), goes full-opacity on hover, and clicking it opens the SAME existing full transcript side panel the header "Transcript" button does (`setShowTranscript(true)`) rather than being a second transcript UI to maintain. Only rendered during live capture (`isMicLive || isBotLive`) and hidden once the full panel is already open. The existing hold-to-talk bar and its above-button utterance-bubble feed (`LiveBars.jsx`) are unchanged.

**Not verified in-browser:** the visual/UX pieces (spacing, shimmer, floating transcript hover/click states) were built and code-reviewed but not screenshotted against the live site — no login credentials available for `tackly.co` in this environment. Worth a manual pass on a real live session.

### Round 4 (same day) — real feedback from "Token Test V5 (Major Changes)", the first real session run after rounds 1-3

**Validation: the round-1/2/3 changes worked.** $0.21 for a 7-minute session (~3¢/min, down from the original $0.0667/min), 21 nodes, and — in the user's own words during the test — "the structure of everything is actually pretty good... looks a lot better than before, not as messy as before." Node classification (including the new `fact`/`plan` types) worked correctly in a real session, not just the synthetic tests from Round 2/3.

**A THIRD over-fragmentation pattern found, via the same real-transcript-review method as Round 2's fix.** Reviewing V5's actual node map turned up ~12 orphan, parentless, empty-summary `waffle`/`idea` nodes with vague auto-generated titles ("Incomplete observation or comparison", "Fragment about page position", "And by default, obviously it shows us") scattered alongside the ~5 well-formed nodes that correctly captured the user's real feedback. Root cause: natural speech pauses/hesitation/self-correction split ONE continuous explanation into several STT utterance fragments, and each fragment — even ones carrying zero content of its own — was getting its own waffle node instead of being silently dropped, because the fragment's real content had already landed on a nearby node. Fixed in `TIER1_SYSTEM`: bucket 1 (SKIP) now explicitly covers mid-thought fragments that are "just connective tissue," and bucket 2 (WAFFLE) gets an explicit test — "if you can't write even a one-sentence summary beyond the title, that's a sign it's SKIP, not WAFFLE" — plus a worked example pulled directly from the V5 fragments. Verified against a reconstructed version of the exact V5 fragment sequence: 4 nodes (1 real + 3 orphan waffle) → 1 node.

**Floating transcript, redesigned based on explicit real feedback** ("it just looks like all of the words together... it would be nice if it was structured like an actual transcript... allow us to scroll... most recent thing visible by default"). `FloatingTranscript.jsx` rewritten:
- Each utterance is now its own bordered bubble (same visual language as the existing hold-to-talk bubbles in `LiveBars.jsx`'s `LiveUtteranceFeed`), not a plain truncated text line.
- Scrollable (`overflow-y-auto`, last 20 utterances instead of 6), auto-scrolls to the newest utterance as it arrives (`scrollRef` + a `useEffect` keyed on the latest utterance id) — chat-style, newest visible by default, scroll up for history.
- The newest bubble gets a periwinkle glow/light-sweep (reusing the `shimmer` animation from the ghost node) until a newer utterance supersedes it — the "glowing purple, light-sweeping" effect asked for.
- Converted the outer container from a plain `<div onClick>` to `role="button" tabIndex={0}` with a keydown handler, matching this project's established pattern for non-`<button>` interactive elements (`NodeCard.jsx` did the same for the same reason — a real `<button>` can't validly contain the inner scrollable region's own interaction).

**Pending/"tackling" node depth, fixed based on explicit real feedback** ("the actual nodes look kind of 2D, 3D-ish [depth]... but this one doesn't, it's flat 2D... if we could do that AND make it look like the other nodes, that would be amazing"). `GhostNodeCard.jsx` now also carries `shadow-brutal` — the same offset drop-shadow every real `NodeCard` has — on top of the light-sweep shimmer added in Round 3, so it no longer reads as flat next to committed nodes.

**Explicitly declined, per direct instruction:** a "timestamped waffle" node type (raised, then immediately retracted, mid-session: *"waffle could be actually — no, forget about it, not a timestamp waffle"*) — not built, correctly not needed.

**Not verified in-browser:** same caveat as Round 3 — the floating transcript's bubble/scroll/glow behavior and the ghost node's new shadow were built and reviewed in code plus verified for classification correctness via `base44 exec`, but not screenshotted live (no login credentials available here).

### Round 5 (same day) — a real bug fix + more real feedback, this time on the board/session lifecycle rather than the LLM pipeline

**Real bug found and fixed: "Linking ideas…" could get stuck forever, even on a session with zero nodes.** Root-caused via code reading (not reproducible through `base44 exec` alone, since it's a React effect-timing bug, not a backend one — confirmed the backend itself converges correctly for a zero-node session in isolation). The wrap-up effect (`Board.jsx`, the one that drives Tier-1 then Tier-2 once after a session ends) depends on `[session, sessionId, refreshSession]` and, partway through, called `await refreshSession()` to check `consolidated_at` before starting the Tier-2 call. That `refreshSession()` call updates the shared `session` state — which is this SAME effect's own dependency — so React tears the effect down (running its cleanup, `stopped = true`) while `consolidate-session` is still in flight. By the time that call resolves, the `finally` block's `if (!stopped) { setPhase(null); ... }` is skipped, because `stopped` flipped to `true` moments earlier — leaving the header stuck on "Linking ideas…" forever even though the backend had already finished correctly. Fixed by fetching the session directly (`Session.get(sessionId)`, no state update) at that one spot instead of going through `refreshSession()` — the shared state still gets refreshed for real, once, in the `finally` block where a resulting effect re-run no longer matters.

**"Tackled 👀" confirmation, added.** Instead of the mapping/linking pill just vanishing with no sense of closure, it now shows "Tackled 👀" for 3 seconds right as the wrap-up finishes (`justTackled` state + timer), then fades.

**Completed, non-continuable threads now say so instead of showing an empty bottom bar.** Previously only bot-meeting threads got a "Continue this thread by voice" CTA when complete (`canContinueByVoice`) — a completed personal (mic) or imported thread had literally nothing at the bottom, which read as broken. New `isDeadEnd` state (`session.status === "complete" && !phase && !canContinueByVoice`) now shows a static "This thread has been tackled 👀" bar, plus a one-time hint bubble above it ("You can still add notes if you need to, otherwise create a new thread.") that shows once per visit and fades after 5s (`showDeadEndHint`/`deadEndHintShownRef`).

**Pending node's dashed border → solid**, per follow-up feedback that dashed read as a "checkered stroke" next to real (solid-border) cards. `GhostNodeCard.jsx` still keeps its shimmer + shadow from Round 4, just no longer dashed.

**Live utterance bubble motion, redone.** Feedback was the bubbles above the hold-to-talk button needed "more motion" on entry and a more "seamless" exit. New dedicated `utterance-in` (slight spring/overshoot arrival) and `utterance-out` (blur + rise + late height-collapse, a softer dissolve) animations in `tailwind.config.js`, replacing the generic `fade-up`/`float-away` for this one component (`LiveBars.jsx`'s `LiveUtteranceFeed`) — left `fade-up`/`float-away` themselves untouched since they're used elsewhere in the app.

**Not verified in-browser:** same standing caveat — no login credentials available here for `tackly.co`. The lifecycle bug fix is a React effect-timing fix verified by code reasoning (and by confirming the backend side converges correctly in isolation via `base44 exec`), not by reproducing the actual stuck-UI state live.

### Round 6 (same day) — tried, then reverted: Tier-2 via Base44's AI Gateway

Briefly moved Tier-2 (`consolidate-session`) off the direct Anthropic call onto Base44's AI Gateway (`base44.aiGateway`, Sonnet) to bill against Base44 credits instead of the Anthropic key. ## 2. Reliability lessons from real meeting testing

Worth reading before touching the Recall integration again. Meeting capture looked done after the initial build but was actually silently broken end-to-end; live testing against a real Google Meet call is what surfaced each of these, in order:

1. **The webhook URL registered with Recall was never reachable.** It was built from `new URL(req.url).origin` inside the Base44 function — but `req.url` inside a Base44 function is always the internal dispatcher address (`base44-dispatcher-production.base44.workers.dev/run/<id>`), never a public one. Every webhook delivery for an entire meeting silently 404'd. Confirmed by deploying a throwaway function that echoed `req.url`/headers back and curling it directly. Fixed by hardcoding the real public domain (`https://tackly.co`) rather than trying to derive it — a `base44-api-url` request header looked promising as a fix but is *also* wrong, because the frontend SDK's default `serverUrl` is a bare `https://base44.app` regardless of what domain the page is actually served from, and that bare host 404s without the app-ID path the SDK uses internally. Lesson: don't try to self-infer a function's public URL from anything request-derived — hardcode the known-good domain.
2. **An uncaught exception in signature verification was 500ing every single webhook delivery.** Once the URL was fixed, deliveries were reaching us (confirmed via logging) but produced zero utterances. Root cause: `atob()` on the verification secret threw `invalid base64-encoded data`, uncaught, which crashed the whole request handler before it ever reached the utterance-creation code — Recall's dashboard showed this as a plain HTTP 500 per delivery. Fixed by wrapping verification in its own try/catch (soft-fail: log and continue rather than reject) and hardening the base64 decode to tolerate URL-safe alphabet/whitespace. Lesson: a "bonus" security layer must never be able to take down the primary data path on a crash — verify defensively, fail open with logging, not closed with a silent 500.
3. **Real-time transcription defaults to `prioritize_accuracy` mode, not low latency.** This produced a genuine ~30s lag between speech and the node appearing, which read as "broken" even though data was flowing correctly. Recall's docs confirm `prioritize_low_latency` mode targets 1-3s webhook updates instead. Fixed in `recording_config.transcript.provider.recallai_streaming.mode`. Note: this only affects *newly created* bots — an already-running bot keeps whatever mode it started with, so testing a mode change requires ending the session and starting a fresh meeting, not rejoining the same one.
4. **The board never re-checked the Session record while a meeting was live.** Even a correct server-side status flip (bot leaving, quota hit, anything) would sit unnoticed indefinitely, because nothing was polling or subscribing to the Session entity itself — only Utterance creates were being watched. Fixed with a realtime `Session.subscribe` + 3s poll fallback while `isBotLive` (same defensive pattern as the utterance ingestion: subscribe for speed, poll because service-role writes can lag on realtime delivery).

None of these would have been caught by code review alone — each needed a real bot in a real call, checked against actual function logs (`npx base44 logs --env preview`), not assumptions about what "should" be happening. Diagnostic pattern that worked well: add a `console.log` at the very top of the handler before anything else executes, deploy, generate one real event, and confirm from the logs whether the function is even being reached before debugging anything downstream.

## 3. Mobile touch fixes + dynamic email-first auth (2026-07-24)

**Board dragging on mobile, fixed.** Individual node cards already had `touch-none` (CSS `touch-action: none`) set on their draggable wrapper, but the canvas PAN surface (`viewportRef` div, `data-pan-surface`, `Board.jsx`) never had it — without it, a touch-drag on empty canvas competes with the browser's own native touch-scroll/pan handling of that element, which is what made panning feel unresponsive/janky on mobile ("can't drag around easily"). Added `touch-none` to the pan surface too, matching what nodes already had.

**iOS auto-zoom-on-focus, fixed globally.** Safari on iOS zooms the whole page in when a text input's *computed* font-size is under 16px — this app's inputs mostly use Tailwind's `text-sm` (14px). Rather than hunting down every input/textarea across the app and bumping its Tailwind class individually (error-prone, easy to miss one), added one rule to `index.css`: `@media (max-width: 640px) { input, textarea, select { font-size: 16px !important; } }`. Desktop sizing is untouched; only mobile-width viewports get the 16px floor.

**Auth rebuilt as a single dynamic, email-first flow.** Previously `/login` and `/signup` were two separate static forms, each always showing both an email AND a password field up front. Now both routes render the same component (`src/pages/auth/AuthFlow.jsx` — `Login.jsx`/`Signup.jsx` are now just one-line re-exports of it, so existing links to either URL keep working unchanged):
1. **Stage "email"** — only an email field + "Continue with email", plus "Continue with Google" above it (unchanged, still first-class). No password field visible at all yet.
2. On submit, a new function (`check-email-exists`) looks up whether that email already has an account (service-role `User.filter`, since `User`'s own RLS is admin-read-only — same pattern as `admin-list-users`) and returns ONLY a boolean, nothing else about the account.
3. **Stage "login" or "signup"**, chosen by that answer — same email shown (with a "Change" link back to stage 1), password field with copy tailored to which one it is ("Password" + "Forgot password?" vs. "Create a password" + the 8-character hint), and the submit button/action wired to `loginViaEmailPassword` or `register`+OTP accordingly. This is the same "does this email exist → branch" pattern most email-first auth flows use (Slack, Notion, etc.) — the accepted tradeoff is that `check-email-exists` is itself a (deliberately minimal) email-enumeration surface: unauthenticated, callable by anyone, returns only `{exists: true|false}`. No rate limiting was added specifically for it (nothing else in this app's auth surface has any either); worth revisiting if abuse ever shows up in logs.
4. **OTP verification redesigned**: `OtpForm.jsx`'s single plain text field replaced with 6 individual digit boxes (`OtpBoxes`, same file) — auto-advances focus per digit, backspace-to-previous, arrow-key navigation, and pasting a full code fills every box at once. Styled to match the rest of the platform (`rounded-xl`, `border-line`, periwinkle focus ring, `font-display` for the digits) rather than a generic browser text input.

**Verified:** `check-email-exists` tested directly against production via `base44 exec` for both a real existing account and a nonexistent address — both returned the correct boolean. The email→branch UI logic and OTP box behavior were built and reviewed in code but not screenshotted live (same standing caveat as prior rounds — no login credentials available here for `tackly.co`).

Action needed was on Google's side (billing/paid tier on the project backing `GOOGLE_T1T2_SECRET`), not the code — `classifyForTier` retries cache creation on every call (nothing permanently disables it), so it starts working the next time a T1/T2 call fires after the quota is fixed.

Root cause: `classify-partial` (Stage 2's live "rough guess" over an in-progress/unfinished utterance — fires constantly during mic/bot capture across solo, meeting, and transcript-import sessions alike) was never migrated off a hardcoded direct Anthropic call when T1/T2 were built — it's a genuinely separate function/endpoint from `process-session`, easy to miss when scoping "T1 and T2" literally. Fixed by routing it through `classifyForTier` under tier `"t1"` (it shares T1's `LlmConfig` row — same fast/live path, just on a partial vs. finalized utterance). Grepped the whole `base44/functions` tree afterward for any other direct-Anthropic call sites — only `admin-set-llm-config` remains, which legitimately needs it for its own test-call mechanism. Verified live via `base44 exec`: correctly classified a partial utterance and, via its cache-attempt log line, confirmed Gemini was actually the model invoked. Incidentally surfaced a useful data point: `gemini-3.5-flash-lite` needs ≥1024 tokens to cache at all (`classify-partial`'s ~275-token prompt got a clean 400 "Cached content is too small" — too small to ever benefit from caching regardless of the free-tier quota block above, harmless, falls back same as any other cache failure).

**LLM models admin card redesigned** (`LlmModelsCard.jsx`) per follow-up feedback that raw always-visible provider/model/secret fields were the wrong affordance: each tier now shows a pulsing "live" dot + the active provider/model, collapsed by default, with a "Change model" button that reveals the edit form (provider/model/secret + Save & Test) rather than the fields sitting exposed all the time. Revert-to-default moved inside that same edit view.

**Real production incident found + fixed, from a live user test ("Gemeni Test" session):** user reported node quality regressions — nodes appearing then disappearing, waffle nodes not persisting, "not as good as Haiku" — and separately shared a Google AI Studio usage screenshot showing ~300 requests with 94 `400 BadRequest` + 19 `429 TooManyRequests` + 2 `404 NotFound`, a ~38% error rate. Root cause: `classifyWithGeminiCached`'s design retried cache CREATION on every single call, with no memory of prior failures. Since cache creation permanently fails for two of the three call sites — T1/T2's larger prompts hit the account's free-tier cached-storage quota (`limit=0`), `classify-partial`'s ~275-token prompt is permanently below Gemini's minimum cacheable size — every classification call was silently making TWO real Gemini requests (one guaranteed-to-fail cache attempt, then the real uncached call) instead of one. This roughly doubled total request volume, which is what actually burned through per-minute rate limits (matches the 429 count) — and critically, a 429 hitting the REAL classification call (not just the wasted cache attempt) fails outright with no retry, which is what most likely produced the appearing/disappearing node symptom directly, independent of any prompt-quality issue.

**Fixed** with a cooldown: added `gemini_cache_retry_after` to `LlmConfig`. After any cache create/use failure, that tier skips cache attempts entirely for 15 minutes (`classifyForTier` checks it before calling `classifyWithGeminiCached`, passing `skipCacheAttempt`) instead of retrying on every call. Verified via `base44 exec`: two sequential T1 calls showed the timestamp set once and left untouched on the second call, confirming the second call skipped the wasted attempt. Investigated via a temporary `admin-inspect-session` function (service-role dump of the session by title, since it belonged to a different account — `jono@candit.co` — than the CLI-authenticated one; deleted immediately after use, same as its two prior uses that day).

**Separately, a real (smaller) classification-quality gap vs. Haiku — not fully explained by the above, worth being honest about:** reading the actual node output against `TIER1_SYSTEM`'s own worked examples (built specifically around Haiku's behavior):
- The utterance "Gemini 3.5 flashlight should be cheaper" (a hedged expectation) was classified as **fact** rather than **opinion** — the prompt's own fact-vs-opinion worked examples call out exactly this kind of hedge language as the opinion signal; Gemini didn't apply it as strictly.
- Two evidence nodes ("Risk note registration confirmed" → "Confirmation of risk note registration support") were created for what's really the same restated confirmation — precisely the REFINEMENT anti-fragmentation pattern the prompt has a dedicated worked example warning against.
- The top-level topic node ended up as a flat catch-all parent for several unrelated sub-threads rather than nesting each under its more specific relevant node.

This may just be an inherent adherence gap between a cheaper/smaller model and a long, example-heavy system prompt tuned against a different model's behavior — not necessarily fixable by more infra changes. Not yet acted on; flagged for a decision on whether it's worth a Gemini-specific prompt tuning pass, or an accepted tradeoff for the cost difference.

**Not verified in-browser:** the admin page's form/test/revert flow was built and reviewed in code, exercised indirectly via the function calls above, but not clicked through live (same standing caveat — no login credentials available here for `tackly.co`).

**Plan vs. idea boundary tightened.** User feedback after the fix above: a plan-shaped utterance got filed as idea. `TIER1_SYSTEM`'s `idea` definition now explicitly contrasts with `plan` ("a SINGLE conceptual suggestion... a direction with steps/a target is plan, not idea"), plus a new worked example alongside the existing plan-vs-topic-vs-action one. ## 7. Live-classification feel: flicker, vanishing nodes, fact-squashing (2026-07-25)

User feedback on a real session ("GPT - Testing Tackly") pointed at two things making the live board feel less real-time than it should, both grounded by pulling the actual node/op history for that session (same `admin-inspect-session`-style temporary function used earlier, deployed, used, deleted).

**Root cause 1 — Stage 2 (`classify-partial`) was re-guessing repeatedly while someone was still mid-sentence.** The real op log showed nodes like `waffle → idea("Analogy or comparison") → idea("AI listening perception") → idea("System summarizing key points automatically")`, three separate type/title rewrites, before the node got hidden entirely — visible flicker plus wasted calls that got overwritten moments later. Root cause: the debounced Stage-2 call in `Board.jsx`'s `handleMicPartial` re-fired on every 500ms tick for as long as an utterance kept extending and stayed under the 0.9-confidence auto-settle threshold. **Fixed**: added `stage2FiredRef`, gating Stage 2 to fire **once** per forming node, reset only when a new node starts forming (on `Node.create`) or an utterance finalizes (`handleMicFinal`). ## 13. RLS security fix — closing public/unauthenticated create access (2026-07-29)

User ran Base44's own security scanner and got 10 "Critical" findings: `CalendarConnection`, `Node`, `NodeEdge`, `NodeNote`, `NodeUtteranceLink`, `Org`, `Session`, `SessionOp`, `SupportTicket`, `UsageEvent` all flagged "Public users can access all X records." Every one of these entities' `read`/`update`/`delete` RLS was already correctly owner-scoped (`created_by`/`owner_email` matching) — the actual hole was `"create": true` on every one of them, meaning any unauthenticated caller could write rows directly, independent of who could later read them back. Real risk: an anonymous caller could spam-create rows, or — since `owner_email` is a plain client-supplied field, not a system one — forge it to a real victim's email and inject content (a fake `NodeNote`/`Utterance`) that would show up in *that victim's own* view via the existing `$or:[created_by, owner_email]` read pattern used on several of these entities.

**First fix attempt used the wrong pattern.** `entities-create.md`'s own documented "Logged-in users only" example is `"create": { "user_condition": { "id": "{{user.id}}" } }` — tried this first, and it failed even for the CLI's own authenticated admin user (`403: Permission denied for create operation on Session entity`), so the self-referential `user_condition.id` comparison doesn't actually work as documented, at least not in this app's deployment. Verified the real fix with a disposable scratch entity (`RlsProbe`, pushed, tested, deleted) rather than trial-and-erroring on production data: `"create": { "created_by": "{{user.email}}" }` — the exact same pattern already used successfully for `read`/`update`/`delete` everywhere in this app — correctly allows an authenticated create (verified via `base44 exec`) and rejects an anonymous one (verified via a raw `curl` POST with no auth header, `403`).

**Applied to all 9 real gaps** (`CalendarConnection`, `Node`, `NodeEdge`, `NodeNote`, `NodeUtteranceLink`, `Session`, `SessionOp`, `UsageEvent`, plus `Org` which now requires admin for create too, matching its already-admin-only read/update/delete — it's entirely unused in the codebase, no legitimate non-admin create case exists). **`SupportTicket`'s public create was left untouched, deliberately** — it's the public `/support` contact form, already paired with admin-only read, which is exactly the Base44-documented-safe "contact form" pattern; it still shows in a scanner as "public create" but isn't actually a gap.

**Verified nothing broke**: every real write path in this codebase already comes from an authenticated caller (frontend routes behind `RequireAuth`, or backend functions relaying the calling user's own auth token) or from a service-role client that bypasses RLS entirely (`recall-webhook`, `recall-status-webhook`) — confirmed by grepping every function that writes to these entities before making the change. Full authenticated lifecycle (session → utterance → node → edge → note → op → usage event, then delete) re-verified via `base44 exec` after the fix; all 9 anonymous-create attempts now `403` via direct `curl` against production.

## 14. Board sharing: Collaborate + Livestream (2026-07-29)

Built directly on top of Finding 13's RLS fix, same session — the sharing feature needed a deliberate design because Base44 RLS can express "the owner can access this" but not "grant access if a row exists in another table naming this other user," which `rls-examples.md` confirms outright: cross-entity relationships need a backend function, not declarative RLS. Two distinct mechanisms, not one flag: **Collaborate** (up to 3 named collaborators, full parity with the owner, persists after the session ends, one person can hold the mic at a time) and **Livestream** (a single view-only link, works for the duration of the session only — dies automatically the moment it completes, no separate on/off toggle needed).

**Data model.** New `Collaborator` entity (`session_id`, `owner_email`, `collaborator_email`, `session_title` denormalized for cheap listing, `invited_at`). `Session` gained `livestream_token` (minted lazily, only valid while `status === "active"`), `active_speaker_email` / `active_speaker_claimed_at` (the mic lock). `Node`, `NodeEdge`, and `NodeUtteranceLink` all gained the same `owner_email` fallback `Utterance`/`NodeNote`/`SessionOp` already had — necessary so a collaborator's own writes (a different `created_by`) still reach the true owner's existing realtime view. `process-session`/`consolidate-session` now stamp it from the session record on every Node/NodeEdge create.

**A real gap found while wiring up the invite function**: `invite-collaborator` creates `Collaborator` rows via service role (needed to enforce the 3-collaborator cap server-side, which RLS can't count), which meant `created_by` on those rows was a service-role identity, not the owner — so the owner couldn't read back their own sent invites under the original RLS (`$or:[created_by, collaborator_email]`, missing the `owner_email` leg). Fixed by adding the same `owner_email` fallback used everywhere else; verified the owner's own `Collaborator.filter()` now returns invites it just sent via the function.

**`get-board-access`** is the single gateway any non-owner uses to view (and, for a collaborator, keep acting on) a board — resolves owner/editor/viewer (owner-email match → editor via a `Collaborator` row → viewer via a matching, still-live `livestream_token` → else 403) and returns a full board snapshot via service role. A non-owner's client polls this every 2.5s instead of subscribing to realtime, since Base44 realtime only ever runs within the *subscriber's* own RLS and can't be extended to someone else's rows without reopening Finding 13's hole. The owner's own view is completely unaffected — still direct realtime, zero added cost for a plain solo session. All 5 access-resolution cases (owner / editor / viewer-valid-token / viewer-wrong-token / viewer-after-session-ended) verified via `base44 exec` against production.

**`mic-lock`** enforces one speaker at a time for Collaborate: claim on hold-to-talk press, release on release, with a 60s staleness window so a crashed client can't permanently strand the lock (same defense-in-depth spirit as the personal-mode `max_session_duration_seconds` cap). Explicitly a best-effort claim, not a true compare-and-swap — two people pressing in the same few milliseconds could both read it as free, accepted since the failure mode is a brief talking overlap, not a security or data issue. All 6 cases (claim-free, re-claim-by-holder, blocked-by-live-holder, stale-claim-overridable, release, no-access-without-being-owner-or-collaborator) verified.

**`invite-collaborator`**: owner-only, enforces the 3-cap and rejects self/duplicate invites server-side, creates the row, and emails the invitee via Resend (new `board_invite` template, reusing the Finding 11 hosted-logo fix) whether or not that email has a Tackly account yet — access resolves the moment they sign up under the same address. `RequireAuth` now preserves the full path+query (not just pathname) through the login redirect, and `AuthFlow.jsx` shows personalized "You've been invited to '\<board\>'" copy when it detects the invite link's `?invited=1&title=` params survived the round trip.

**Frontend**: Home's "Your boards"/"Shared boards" tabs (the latter reads `Collaborator` rows directly — no function needed, RLS already scopes reads to the invited email); a new `ShareDropdown` (owner-only, a clickable "Livestream / Share" text link next to AI Assistant, per explicit request — not a full button) with the lazily-created watch-link and collaborator management; `MicBar` (`LiveBars.jsx`) took two new optional props (`onClaimMic`/`onReleaseMic`/`blockedBy`) so mic-lock is fully backward-compatible — a plain solo session passes neither and behaves byte-identical to before. Viewer role hides hold-to-talk, "continue by voice," node dragging, and note-adding in the UI, backstopped by RLS either way (a viewer has neither ownership nor a `Collaborator` row to write against, so even a missed UI gate would just 403).

**A pattern that repeated from Finding 11's owner_email bug, found again here**: three more frontend write sites (`Board.jsx`'s live-capture `Utterance.create`, `NodeNote.create`, and the `appendUserOp` `SessionOp.create` helper) were all stamping `owner_email: user?.email` — the *current speaker's* email, not necessarily the session's real owner. Harmless for a solo session (they're the same person) but would have silently stranded a collaborator's utterances/notes/ops outside the true owner's view the first time anyone actually collaborated. Fixed all three to use `session?.owner_email` first.

**Verified end-to-end via `base44 exec` against production**, simulating a full collaborator round-trip (a session owned by a different email than the acting CLI user, that user added as a collaborator): `get-board-access` correctly resolves "editor"; a node created by the "collaborator" is correctly stamped with the *true* owner's email and is visible through the collaborator's own subsequent poll; mic-lock claim/block both work; and when the same session also has a valid livestream token, editor access correctly takes precedence over viewer. **Not verified in-browser**: the actual click-through UI (dropdown layout, tab styling, the "X is speaking" indicator in a real live session) — no login credentials available here, so this was a clean production build plus the backend integration test above, not a live click-through.

## 15. Production rollback, the "owner falsely enters shared mode" bug, and the Gemini-speed false alarm (2026-07-29)

Shortly after Finding 14 shipped, the user reported the live site felt "extremely slow" — even for plain solo sessions, not just shared ones — and rolled `tackly.co` back to `35a6764` (the last commit before the RLS fix and Collaborate/Livestream work), via a `good-version` branch, while keeping the new work on `main`/`feature/collab-boards` to fix before relaunching. (The user had manually copied `collaborator.jsonc` into `good-version` so the entity itself wouldn't be dropped if they ever pushed entities from it — worth knowing since it briefly looked like a Base44 platform quirk before they clarified it.)

**Root cause, found by reading the actual code path rather than guessing**: `Board.jsx`'s non-owner fallback (`loadShared`, Finding 14) called `setSharedRole(role)` unconditionally whenever the owner-scoped `loadInitial()` failed for *any* reason. But `Session.get()` 404s identically whether a session truly doesn't exist or RLS is just hiding it from a non-owner (verified directly: a real non-owner request produces `404: Entity Session ... not found`, not a distinct 403) — so a transient failure on the OWNER's OWN load (a timeout, a rate limit, anything, among `loadInitial`'s 6 parallel queries) looked exactly like "not the owner" from that code's point of view. And `get-board-access` always resolves the true owner as `role: "owner"` too, since owner-email match is its first, highest-priority check — it has no way to know the call came from this specific fallback path. Once triggered, the owner was silently and *permanently* downgraded for the rest of the visit: polling every 2.5s instead of realtime, **and** wholesale-replacing the entire nodes/edges/utterances arrays each poll instead of applying incremental ops — while the real realtime subscription kept running in parallel, fighting it. This combination explains the reported symptoms end to end (pulled from the user's own recorded "Updates for Claude" feedback session, read via `admin-inspect-session`): nodes stuck 5-10s, the tackling ghost lingering, transcript bubbles showing stale content, everything getting worse the longer the session ran (more nodes = more re-render cost per wholesale replacement).

**Fixed**: `loadShared()` now only calls `setSharedRole()` when `get-board-access` resolves a genuinely different role (editor/viewer). If it resolves "owner," the original failure was spurious — the snapshot is adopted but the board stays on its normal realtime path, never entering polling mode. ## 17. Gemini T1 caching was silently broken since activation — the real "T1 feels slower" cause (2026-07-30)

Same day as the RLS/Collaborate work (Findings 13-16), the user reported the live-capture "T1" fast path — a spoken thought going from a raw waffle placeholder to a properly typed, connected node — now took 4-5 seconds instead of feeling instant, on both home wifi and a mobile hotspot. Given Finding 15 had already investigated a Gemini-speed complaint days earlier and concluded "transient," the instinct to dismiss this the same way was resisted — this time by reading the actual function logs instead of re-measuring perceived latency.

**Root cause 1 — every cached Gemini call has 400'd since caching was ever turned on.** `classifyWithGeminiCached`'s cached `generateContent` request (`shared/gemini.ts`) set `toolConfig` in the same request body as `cachedContent`. Google's API rejects that combination outright: `400: CachedContent can not be used with GenerateContent request setting system_instruction, tools or tool_config` — confirmed verbatim in `process-session`'s own logs (`npx base44 logs --function process-session`). `system_instruction`, `tools`, and `tool_config` are documented as immutable, input-only properties of the `CachedContent` object itself, not the per-call request — so every single cached call has been failing and silently falling back to the plain uncached path (which correctly sets `toolConfig` on the per-call request, since it has no cache to conflict with) since Gemini explicit caching was activated on 2026-07-24 (Finding 4). That means T1's entire multi-thousand-token classification system prompt has been reprocessed from scratch on every utterance, the whole time, with the caching feature never once actually delivering its speed/cost benefit — a standing bug hiding behind "fails soft by design," which is correct fallback behavior but was masking a real, permanent failure rather than an occasional one. **Fixed**: moved `toolConfig` into `createGeminiCache`'s request body (where it belongs, alongside `systemInstruction`/`tools`) and removed it from the per-call cached request.

**Root cause 2 — `classify-partial`'s prompt is permanently too small to cache, and was poisoning `process-session`'s shared cache state.** `classify-partial` (provisional-node stage 2, [PLAN.md §11](PLAN.md#provisional-nodes-staged-classification)) intentionally shares tier `"t1"`'s `LlmConfig` row with `process-session` — one admin control knob for "whatever provider T1 runs on" governs both. But `classify-partial`'s system prompt is a fixed ~300 tokens, permanently below Google's 1024-token minimum for explicit caching (`400: Cached content is too small. total_token_count=295, min_total_token_count=1024`, also confirmed in logs) — this is deterministic, not transient; retrying it later never helps. Since `classify-partial` fires constantly during live mic capture (every debounced partial guess), and every failed cache attempt resets the shared 15-minute `gemini_cache_retry_after` cooldown on tier `t1` (the anti-429-storm mechanism from Finding 4), `classify-partial`'s guaranteed failures kept re-poisoning the cooldown window `process-session` needed to ever establish and reuse a cache for its own, much larger, genuinely cacheable prompt — even after root cause 1 was fixed. **Fixed**: added `allowGeminiCache` to `classifyForTier` (`shared/llm.ts`); `classify-partial` passes `false`, skipping cache logic entirely and going straight to the plain call it already needs, without ever touching `t1`'s shared cache/cooldown state.

**A third issue, found during live verification, not guessed at**: Google's cache-specific endpoints (`cachedContents` create, and cached `generateContent`) were observed hanging past a newly-added 6-second timeout on every single call in the user's own real "Test T1 Fix" session — `npx base44 logs` showed 7/7 `process-session` calls in that session logging `"Gemini cached generateContent failed, falling back to uncached call: The operation was aborted"`. A 524 gateway timeout had also shown up earlier in isolated testing. Neither cache fetch had a timeout of its own originally, so a slow/unhealthy stretch on Google's side could stall a classification indefinitely instead of just falling back — caching must never be allowed to make T1 slower than not caching at all. **Fixed in two steps**: added a bounded `fetchWithTimeout` (`AbortController`) around both cache-specific fetches, first at 6s, then — once the real session's logs showed the endpoint consistently hanging at/near that exact bound rather than occasionally — shrunk to 2s, so a bad stretch costs far less before falling back, while still leaving room for a genuinely fast cache response to succeed.

**Verification method**: exclusively `npx base44 logs --function process-session/classify-partial --env preview` (real function logs, not synthetic assumptions) plus `base44 exec --privileged` against disposable test sessions — created real utterances, invoked `process-session`/`classify-partial` directly, confirmed the exact 400 in logs before each fix and its absence after, confirmed `LlmConfig.gemini_cache_name` actually populates and persists (with a valid `gemini_cache_expires_at`) on a real call once both root causes were fixed, and confirmed correct classification output (accurate node type/title, correctly parented/positioned) through both the now-working cached path and `classify-partial`'s isolated uncached path. Test data cleaned up (nodes/edges/utterances/sessions deleted) after each round. One limitation flagged honestly to the user: the verification environment's own network was intermittently unreliable during this session (repeated `ECONNRESET`/"socket hang up" on outbound calls to the Base44 API), so a clean stopwatch "before vs. after" number couldn't be captured directly — the fix itself rests on the log evidence (a deterministic, documented API rejection, now gone) rather than a timing benchmark.

**User re-tested live after all three fixes landed and confirmed**: "it's fine... its perfect, as it was before basically" — T1 kept on Gemini, no provider switch, by explicit user choice (offered given two separate signs of Gemini cache-endpoint instability in one session, same kind of judgment call as Finding 15's). Further speed work (e.g. investigating whether Gemini's baseline uncached latency itself can be improved, given even the reliable fallback path ran several seconds in places during testing) was explicitly deferred by the user to a later session, not treated as urgent once T1 felt right again.

**Deployed**: `functions deploy` across three rounds (toolConfig fix; `allowGeminiCache` isolation + initial 6s timeout; final 2s timeout tuning) — no entity schema or frontend changes, so no `entities push` or `site deploy` needed. Each round confirmed via fresh `base44 exec` checks before moving to the next.

## 18. Correction to §17 — the slowness was never Gemini, it was the cache-serving endpoint; caching disabled by default (2026-07-30)

Same day, a few hours after Finding 17 shipped and the user re-tested and confirmed it felt right. Then it recurred: node placement/connection ("T1's second half" in the user's words — really still `process-session`, see the terminology note below) went slow and unreliable again, this time with real `500`s visible directly in the Base44 dashboard (`api.function.call`, `status_code: 500`, two entries ~15s apart) during the user's own live test on a session named "Test T2 Fix?".

**The user pushed back on the framing, correctly.** The instinctive next move was to suggest switching T1 off Gemini onto Claude Haiku — the user firmly rejected this: *"It's not gemeni though - gemeni is fast, and it always has been - this wasn't an issue before when we were using gemeni... no switching to haiku."* They asked for the actual pipeline to be understood instead, and pointed at the `good-version` branch (confirmed identical to commit `35a6764`, already diffed against in Finding 17 — process-session/consolidate-session/classify-partial/shared/llm.ts/shared/gemini.ts/shared/claude.ts were all byte-for-byte identical there except the trivial `owner_email` additions from Finding 14) as proof "not much has changed."

**They were right, and the real explanation is a subtle one.** Isolating variables live: a clean batch of 6 `process-session` calls with Gemini caching **disabled** (`allowGeminiCache: false`, the classify-partial-only escape hatch from Finding 17) all succeeded in **2.0-3.3 seconds each, zero failures**. The exact same model, same system prompt, same everything — genuinely fast and reliable, exactly matching the user's own memory of "before." Every prior slow/failed call, across every test that day, had gone through the **cached** path specifically. Re-checking logs: every single "aborted" warning said `Gemini cached generateContent failed` — never once a plain uncached failure. One uncapped test (before a timeout existed on this path) ran **33+ seconds and still failed**.

**Conclusion**: Gemini's plain `generateContent` endpoint has been fast and reliable the entire time, including throughout Finding 17 — the user's instinct was correct. What's actually slow, intermittently but consistently across an entire day of testing, is Google's **`cachedContent`-referencing** `generateContent` endpoint specifically — a genuinely different code path on Google's infrastructure (looking up and joining stored cache content is not the same operation as a plain generation call), independent of whether the cache was just freshly created or had already existed and was simply being reused.

**Why this only surfaced now, not when caching first activated on 2026-07-24**: Finding 17's root cause 1 (the `toolConfig`-alongside-`cachedContent` bug) meant every cached call failed with a fast, near-instant `400` from day one — so in practice, T1 has ALWAYS run on the fast, reliable plain path, with the caching layer silently and harmlessly short-circuited the entire time. Fixing that bug (correctly, by the letter of Google's own docs) made caching actually start working for the first time — which is exactly what exposed the cache-serving endpoint's own, unrelated slowness. The fix for Finding 17 was correct; it just revealed a second, independent problem that had been masked by the first one.

**Fixed**: `classifyForTier`'s `allowGeminiCache` flipped from opt-out to opt-in (`shared/llm.ts`) — caching is now off by default for every tier (`t1`/`t2`/`chat`), not just for `classify-partial`'s permanently-too-small prompt. Gemini stays the active provider throughout; nothing about the model, system prompts, or classification logic changed — only whether a request references a cache. `classify-partial`'s explicit `allowGeminiCache: false` was left in place (now redundant against the new default, but still documents that this specific call site should never opt back in even if caching is re-enabled elsewhere later, since its prompt can never meet Google's minimum cacheable size).

**Verified live**: 6/6 fresh `process-session` calls succeeded in 2.0-3.3s each with zero cache-related log warnings; `consolidate-session` (T2) separately verified clean at 1.8s. Test session cleaned up after.

**A terminology note worth keeping straight**: the user's "T1 is split between two things, fast path and then something else" and "T2... assigns that node somewhere sensible" both describe real, distinct behavior — but per this codebase's own naming, both halves are still **Tier 1** (`process-session`): stage 1/2 are the instant placeholder + `classify-partial`'s debounced rough guess (PLAN.md §11), and the "does it get placed/connected properly" step the user was actually complaining about both times is Tier 1's own authoritative finalization on `end_of_turn` — not Tier 2 (`consolidate-session`), which is the separate periodic (every 20 utterances) merge/cleanup pass and hadn't even run yet in either test session. Worth clarifying with the user directly rather than silently renaming anything, since "T1 vs T2" as a mental model may be worth revisiting in the UI/docs if it keeps causing this mismatch.

**Deployed**: `functions deploy` (one round). No entity schema or frontend changes.

**✅ STABLE BASELINE — confirmed by the user in live use after this fix**: *"thats good - it's at a stable stage again. Things are rendering, not taking forever."* This is the reference configuration for the live rendering pipeline going forward:

- Tier 1 (`process-session`) and Tier 2 (`consolidate-session`) both run on Gemini (`gemini-3.5-flash-lite`, `GOOGLE_T1T2_SECRET`) via the plain, **uncached** `generateContent` call — `LlmConfig.provider = "google"`, Gemini explicit caching present in code but **off by default** (`allowGeminiCache` opt-in, not opt-out — see `shared/llm.ts`).
- `classify-partial` (provisional stage 2) explicitly passes `allowGeminiCache: false` regardless of the default, since its prompt can never meet Google's cacheable-size minimum.
- The last-resort Gemini call has a 15s timeout + one automatic retry (`shared/gemini.ts`); the (currently unused, opt-in-only) cache-specific calls remain bounded at 2s.
- Typical live latency at this baseline, measured directly: **T1 ≈ 2-3s per utterance, T2 ≈ 1-2s**, both reliable (0 failures across clean repeated testing).

**Do not re-enable Gemini caching (`allowGeminiCache: true`) without first re-verifying Google's cache-serving endpoint is actually fast again** — re-enabling it blind would silently reintroduce the exact regression this and Finding 17 fixed. If a future session wants to chase T1/T2 latency further below this baseline, treat this configuration as the floor to beat, not a problem to route around.

## 20. T1 authoritative placement was gated behind a flat 2500ms batching delay (2026-07-30)

Same day, after the Gemini-caching fix (Findings 17-18) already brought T1/T2 down to a 2-3s baseline, the user asked why real-time placement still felt slow — pointing at `BATCH_DEBOUNCE_MS = 2500` in `Board.jsx` and asking whether it could safely drop to 600-800ms, and whether Tier 1 was really supposed to already understand when it had "enough context" for a provisional node (with Tier 2 correcting later if needed).

**Traced the full staged-provisional pipeline** (`Board.jsx`, live mic path) to answer both questions precisely:
1. **Stage 1** — instant raw placeholder node, no LLM, fires on the first 3+ words of a partial transcript.
2. **Stage 2** (`classify-partial`, 500ms debounce, once per forming node) — the "T1 already understands context" the user was thinking of; settles the card's type/title early in ~90% of cases.
3. **Stage 3** (`process-session`, on `end_of_turn`) — the actual **authoritative** placement: commits the real type, parent, and edges. This is the step that matters for "is it actually on the board yet," and it's not what the user's mental model of "T2 corrects" maps to — Tier 2 (`consolidate-session`) is a separate periodic merge pass every 20 utterances, uninvolved in single-utterance placement at all (same terminology point already made in Finding 18).

**The bug wasn't accuracy, it was a pure cost-batching tax stacked in front of Stage 3.** `queueForProcessing` (`Board.jsx`) queued each finalized utterance and only flushed to `process-session` after `BATCH_DEBOUNCE_MS` (2500ms) of silence, or once 4 utterances queued (`BATCH_MAX_SIZE`) — added originally (PLAN.md §1d) to avoid paying `process-session`'s fixed system-prompt/tool-use overhead once per utterance. In the common case (one utterance, then a pause) this meant waiting nearly 2.5s for the authoritative call to even *start*, on top of its own 2-3s round-trip — a worst case around 5s from finishing a sentence to it landing as a real, connected node, with nothing in that wait actually doing useful classification work.

**Fixed**: `BATCH_DEBOUNCE_MS` dropped from `2500` to `700` (`Board.jsx:606`). `BATCH_MAX_SIZE` (4) is unchanged and still batches genuine rapid-fire utterances together; the real-world cost impact is a modest bump in `process-session` call *count* in the normal single-utterance case, not a change in per-call cost (same prompt either way).

**Verified**: production build + `site deploy`, asset hash confirmed live via `curl` against `tackly.co`. User tested live afterward and confirmed: *"i just tested it out... It works!"*
